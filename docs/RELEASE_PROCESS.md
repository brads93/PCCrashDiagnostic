# Release process

This process creates evidence-backed candidates. No workflow in this repository
publishes a GitHub release or changes `ShareApproved` automatically.

## 1. Source gate

- Review every dependency and lock-file change.
- Confirm CODEOWNERS and enable branch/tag protection.
- Require a clean tree and exact tag `v3.2.0-beta.1`.
- Confirm `global.json` pins SDK `10.0.400` and the release pins runtime
  `10.0.11`.
- Run ShareReadOnly CI and retain the restricted raw TRX artifact.
- Require the locked NuGet vulnerability audit and public IL/resource audit to
  pass; only aggregate counts are included in `TestEvidence.json`.

## 2. Candidate construction

Run from a clean tagged checkout:

```powershell
.\tools\Build-Release.ps1 -OutputRoot C:\release-candidates -RequireExactTag
```

The candidate contains a runtime ZIP, source ZIP, schema-3 release manifest,
and checksum file. The runtime ZIP contains one executable plus documentation,
sanitized `TestEvidence.json`, an SPDX 2.2 SBOM generated by the pinned
Microsoft SBOM Tool 4.1.5, and an unattested in-toto/SLSA
provenance statement.

The SBOM and provenance are useful evidence, but neither is a third-party
attestation or a claim of a SLSA level.

## 3. Signing

Follow [CODE_SIGNING_POLICY.md](../CODE_SIGNING_POLICY.md). The protected
SignPath workflow signs only the main executable and rebuilds the candidate
around the signed bytes. It requires the exact tag and a pinned signer
thumbprint, subject, and issuer. Its output is still **signed awaiting VM**, not shareable.

## 4. External release gates

Independently verify the RFC 3161 timestamp. Then test the exact finished
runtime ZIP in fresh disposable Windows VMs. Bind all evidence to the package
SHA-256 using [EXACT_PACKAGE_VM_CHECKLIST.md](EXACT_PACKAGE_VM_CHECKLIST.md).
Any byte change requires repeating the affected checks.

After reviewing a sanitized evidence JSON matching
`.config/release/ExactPackageVmEvidence.schema.json`, run
`tools/Finalize-Release.ps1` with the explicit tested ZIP SHA-256 and
`-ApproveForSharing`. The finalizer may produce a manifest with
`CandidateState=ApprovedForSharing`, `ShareApproved=true`, no blockers, valid
Authenticode, verified RFC 3161, and verified exact-package VM evidence. That
step updates only the outer manifest/checksums and proves the copied runtime ZIP
hash is unchanged. It never publishes. Until this succeeds, the output is a candidate.

## 5. Reproducibility and provenance comparison

For unsigned builds, use the same clean commit and `SOURCE_DATE_EPOCH`, build
twice into separate output roots, and compare the runtime/source ZIP hashes.
Authenticode normally changes the executable bytes, so compare a signed build
against its recorded unsigned input and signing request rather than expecting
it to match the unsigned ZIP.

Review:

- `ReleaseManifest.json` and `BUILD-MANIFEST.json`;
- `TestEvidence.json` against the restricted raw TRX hash;
- `SBOM.spdx.json` against committed `packages.lock.json` files. The pinned
  tool targets .NET 8, so release builders also require the build-only
  Microsoft.NETCore.App 8.0.30 runtime; it is not included in the app package;
- `Provenance.intoto.json` subjects/materials against the build inputs; and
- `SHA256SUMS.txt` against the final directory.

The verifier can validate a candidate without launching it. Add
`-RunSmokeTest` only in an appropriate trusted test environment. A final gate
must use `-RequireShareApproved`.
